# AirborneDiag

面向民机机载系统的智能故障诊断工程，结合大语言模型、领域知识库与诊断工具，对故障记录进行分析，输出诊断依据、候选原因及排查和处理建议。

## 当前状态

项目处于原型开发阶段：首版完整诊断流程已可用，覆盖 MPC5554 的 FlexCAN2 与 DSPI 首批场景。

已建立可安装的 Python 包与命令行入口，可执行 `airbornediag --help` 和 `airbornediag --version`。安装与最小测试已在 Windows 和 RDC300I（Linux ARM64，Python 3.9.9）的独立虚拟环境中验证通过，环境配置与板端离线安装步骤见 [docs/development.md](docs/development.md)。

已定义故障记录与诊断报告的输入输出契约（格式版本 0.1.1），以 JSON Schema 声明字段约束并实际执行校验，并给出首批诊断场景（MPC5554 的 FlexCAN2 与 DSPI）及对应示例。**契约、Schema、示例与校验已建立；按位解释寄存器原始值尚未实现。**

已实现对 MindIE 模型服务的调用，可用 `airbornediag llm --prompt "..."` 向已部署的 Qwen2.5-1.5B-Instruct 发送一段文本并取回回答，用于验证服务连通性。接口依据板端已验证可用的历史脚本，服务地址、模型名、超时与认证信息均可配置。已在 RDC300I 上对真实服务验证通过；调用失败时一律报错，不返回模拟回答。

已建立首批 MCU 诊断知识库并实现全文检索。知识条目整理自 MPC5553/5554 参考手册，覆盖 MPC5554 的 FlexCAN2 与 DSPI，每条保留来源、章节与表/图编号；检索用 Python `sqlite3` 的 FTS5 实现，可用 `airbornediag kb build` 构建索引、`airbornediag kb query "总线关闭"` 查询，支持按芯片和外设过滤、限制返回条数。索引为本地生成物，不提交仓库，在目标机器上重建。已在 Windows 与 RDC300I 上验证构建与检索结果一致。**知识来源为芯片手册原文；按位解释寄存器原始值尚未实现。**

已实现首批 MCU 诊断工具，可用 `airbornediag diag examples/REC-2026-0918-002.json` 读取故障记录并按固定规则分析其中的已解码位域，输出确认的状态、输入中的矛盾、因缺失而无法判定的内容以及本版不支持的范围；每条结论都带手册出处与对应的知识条目。工具覆盖 MPC5554 的 FlexCAN2（`CAN_A`、`CAN_B`、`CAN_C`）与 DSPI（`DSPI_A`～`DSPI_D`），可脱离模型服务独立运行，也有便于机器读取的 `--json` 输出。已在 Windows 与 RDC300I 上对示例记录验证输出一致。**工具只使用记录中已解码的位域：只给出原始值的观测、以及已观测但本版没有判据的位域都不参与判断，并按不支持列出。**

已打通完整诊断流程，可用 `airbornediag report examples/REC-2026-0918-002.json` 一条命令完成输入校验 → 工具分析 → 知识检索 → 模型分析 → 报告输出。流程由程序固定编排：工具结论、观测回显、缺失信息与不支持项由程序组装进报告，模型只负责解释、候选原因与检查建议，候选原因中的证据引用只能是记录里已有的观测。报告在输出前过一遍输出契约校验，不合规即不输出。原有 `diag`、`kb`、`llm` 子命令保持不变，可单独使用。

`examples/` 下有 10 条模拟故障记录，逐条对应一种情形：四个首批场景，以及确认与不可判定的对照、只听模式抑制、错误标志快照、多实例、部分对象不支持等，每条都配有 `tests/fixtures/` 下的期望报告。可用于人工核对改动前后的完整流程，清单见 [docs/scenarios.md](docs/scenarios.md)。

**真实模型服务联调已完成**（2026-09-24 两条示例，2026-09-28 新增 8 条各一次；Windows 侧经端口转发调用板端 MindIE）：报告的程序组装部分与工具结论逐条一致，8 条新增案例的程序组装部分也与期望报告一致；但模型给出的候选原因始终为空，并在检查建议中出现过材料里不存在的名称，以及直接把观测 id（`OBS-1` 等）当作检查建议。2026-09-28 针对提示词与解析做过一轮修正（去掉会被照抄的示例、要求候选原因至少引用一条观测、取消会改变送入证据的硬截断），复测未再出现回答结构不合规，候选原因仍为空——**当前知识库缺少成因类条目，按"知识与观测共同支持才提出"的口径给不出候选原因**。**流程可用，模型分析部分的质量目前不达预期**，已知问题与验证范围见 [docs/development.md](docs/development.md)。

首版聚焦 **MPC5554、TMS320F28335 等机载控制器设备 MCU 的片上资源及外设故障**，采用自主设计的 JSON 故障记录验证完整诊断流程，后续逐步接入实际控制器数据。

## 首版目标

* 定义统一的 JSON 故障记录与诊断报告格式。
* 基于芯片手册和检测定义构建可追溯的知识库。
* 通过固定工具完成知识查询、状态解析和规则判断。
* 接入 Qwen2.5-1.5B-Instruct，生成结构化故障分析。
* 使用模拟案例验证诊断结果，并在 RDC300I 平台上开展运行测试。

## 处理流程

故障 JSON 输入 → 数据校验 → 诊断工具与知识检索 → Qwen 分析 → 输出校验 → 诊断报告。

报告区分已确认的异常与待验证的候选原因，提供引用依据、缺失信息和后续检查建议。首版仅生成处理建议，不自动执行设备控制操作。

## 技术方案

* **开发语言**：Python 3.9
* **推理模型**：Qwen2.5-1.5B-Instruct
* **推理服务**：MindIE
* **知识检索**：SQLite FTS5 全文检索（标准库 `sqlite3`，不引入向量模型或独立数据库服务）
* **开发环境**：Windows
* **目标运行平台**：RDC300I

模型权重独立于代码仓库管理，应用通过模型服务接口调用推理能力。

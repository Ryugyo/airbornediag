# 文档维护规则

## 基本原则

1. 文档记录有长期价值的信息，帮助理解、使用和维护工程。
2. 同一类详细信息只在一个位置维护，其他文档通过链接引用。
3. 文档更新由内容变化触发，不要求每完成一个任务就修改文档。
4. 当前说明应反映当前状态；更新时清理失效表述，不只追加新段落。
5. 明确区分“已实现”“已确定但未实现”“待决定”。
6. 不将讨论草稿、模型推测或临时试验结果写成已确认结论。

## 文档职责

| 文件 | 负责的内容 | 不负责的内容 |
|---|---|---|
| README.md | 项目简介、当前能力与范围、可用的快速开始、面向读者的文档入口 | 详细架构、完整字段定义、开发流水账 |
| CLAUDE.md | 开发助手工作约定、Claude 的读取入口、验证要求和Git边界 | 详细业务设计、当前任务记录 |
| docs/architecture.md | 模块职责、核心数据流、部署关系及关键边界 | 完整接口字段、调试过程、逐次修改清单 |
| docs/contracts.md | 输入输出字段语义、缺失值约定、格式版本规则及已知限制 | 完整字段清单（以 Schema 为准）、具体诊断判据 |
| docs/scenarios.md | 首批诊断场景、判据依据、适用条件与支持范围 | 字段结构定义、寄存器解析实现细节 |
| docs/development.md | 经过验证的环境配置、运行、测试、部署和常见排障方法 | 详细架构设计、业务判据 |
| .claude/rules/documentation-rules.md | 文档职责、更新条件和一致性维护方法 | 具体业务设计和开发进度 |

## 更新条件

| 变化 | 更新位置 |
|---|---|
| 项目定位、当前支持范围或用户使用方式变化 | README.md |
| 模块职责、核心流程或部署关系变化 | docs/architecture.md |
| 输入输出字段、缺失值约定或格式版本规则变化 | docs/contracts.md 与 schemas/ |
| 诊断场景、判据依据或支持范围变化 | docs/scenarios.md |
| 环境配置、运行或部署方法变化 | docs/development.md |
| 开发约定、读取入口或Git操作边界变化 | CLAUDE.md |
| 文档组织与维护约定变化 | 本文件 |
| 普通内部实现或局部Bug修复，未影响上述内容 | 通常不需要更新工程文档 |

若变更影响多份文档，只分别更新各自负责的内容，不复制同一段详细说明。

## 后续文档按需建立

以下文件在有实际内容时再创建：

- docs/decisions.md：重要技术取舍的背景、选择、理由、代价与状态。

内容较多、主题可以独立维护时再拆分文件或目录。未建立的文档不加入有效文档链接。

不为每个任务建立独立设计文档，不默认维护开发日志或调试日志。任务过程和验证结果优先保留在Issue、PR或任务汇报中；可复用的结论再整理到工程文档。

## 一致性与来源

1. 目录、命令、配置项和功能说明应核对实际工程状态。
2. 尚未执行验证的命令应明确标记，不放入已可用的快速开始。
3. 文档说明预期设计，代码和测试用于核实实际行为；发现冲突时指出差异，判断应修复实现还是更新说明。
4. 后续建立数据模型或Schema后，字段结构尽量引用或生成，说明文档重点解释语义和约束，避免手工维护两套完整字段清单。
5. 架构文档链接必要的代码入口，不维护容易失效的代码行号或完整源码副本。
6. 芯片知识和诊断依据应保留文档名称、版本及章节或页码。
7. 重要决策被替代时标明替代关系，不将历史决定继续描述为当前方案。

## 修改后检查

- 文档与实际变更是否一致；
- 相对链接和文件路径是否有效；
- 规划内容是否被误写为已实现；
- 是否残留矛盾或失效描述；
- 是否重复维护其他文档已有的详细内容。

任务汇报中简要说明实际更新的文档即可，不要求填写固定的长篇文档变更报告。

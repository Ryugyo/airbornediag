# AirborneDiag 架构说明

## 当前状态

当前工程已建立可安装的 Python 包、命令行入口和测试，定义了输入输出契约与首批诊断场景，实现了对 MindIE 模型服务的调用，并建立了首批 MCU 诊断知识库与全文检索；诊断业务功能尚未实现。

本文记录已确定的模块划分和首版处理流程。除目录、命令行入口、包配置、契约、首批场景、知识库与检索、模型调用外，所述组件均为待实现设计；具体实现细节在对应开发任务中确定。环境配置、安装、知识库构建与查询、模型服务接口与测试方法见 [development.md](development.md)，字段语义与约束见 [contracts.md](contracts.md)，场景与判据依据见 [scenarios.md](scenarios.md)。

## 首版处理流程

统一故障JSON输入 → 数据校验 → MCU相关工具分析与知识检索 → Qwen综合分析 → 输出校验 → 结构化诊断报告。

首版由程序固定编排处理步骤，不依赖模型自主选择工具。

输入采用模拟故障记录。未来通过控制器专用适配器转换实际记录，复用统一诊断流程。

|---|---|
| src/airbornediag/ | 应用入口、配置、数据模型和诊断流程编排 |
| src/airbornediag/llm/ | 模型服务请求、响应处理及提示词 |
| src/airbornediag/knowledge/ | 知识离线构建与运行时检索代码 |
| src/airbornediag/mcu/mpc5554/ | MPC5554专用解析与诊断逻辑 |
| src/airbornediag/mcu/tms320f28335/ | TMS320F28335专用解析与诊断逻辑 |
| knowledge/sources/ | 本地原始芯片资料 |
| knowledge/curated/ | 经核对的知识、检测定义和规则依据 |
| knowledge/index/ | 本地生成的全文检索索引，不提交仓库 |
| schemas/ | 输入输出契约的 JSON Schema 声明 |
| examples/ | 面向使用者的演示输入 |
| tests/fixtures/ | 回归测试输入及预期结果 |
| scripts/ | 知识构建、批量评估等辅助入口 |
| docs/ | 工程设计与开发说明 |

`knowledge/source-registry.json` 集中登记工程内可引用的文献来源，诊断结论只引用其 `id`，不重复文献元数据。

应用包内已建立：

- `__init__.py`：包定义与版本号。
- `cli.py`：命令行入口，支持使用说明、版本查询与 `llm`、`kb` 子命令。
- `config.py`：配置加载与校验，当前只包含模型服务配置。
- `llm/`：模型服务调用。`client.py` 负责请求与响应处理，`prompt.py` 负责提示词构造。
- `knowledge/`：知识读取、索引构建与查询，不依赖模型服务。`model.py` 负责知识文件读取与出处校验，`index.py` 负责索引与检索。

后续计划在应用包内按需建立：

- schemas.py：输入、输出及内部数据模型。
- pipeline.py：诊断流程编排。

这些文件尚未实现。独立职责初期可以由单个文件承担，内容增长后再拆分为包。

## 核心边界

### 统一输入与控制器适配

统一JSON描述目标MCU、检测上下文和观测信息，字段约束由 [schemas/](../schemas/) 下的 JSON Schema 声明，语义与缺失值约定见 [contracts.md](contracts.md)。

控制器原始PBIT记录的解释依赖控制器型号、软件版本和检测定义。未来输入适配器负责这类转换，不将控制器专有故障码混入通用MCU逻辑。

缺失信息表示未知，不能自动转换为正常状态或默认测量值。

### MCU工具与诊断编排

MCU模块负责有依据的寄存器解码、状态解释和专用判据计算。

工具结果应能够表达：

- 解析得到的事实；
- 适用的规则及来源；
- 数据不足或不适用的原因；
- 有依据支持的候选结论。

流程编排负责组合相关工具和检索结果。后续跨外设关联分析由流程组织，避免各MCU模块自行复制整套诊断流程。

未实现或未验证的故障类型应明确报告支持范围，不能默认为正常。

### 知识资料与知识处理代码

根目录knowledge/保存资料及整理后的知识；src/airbornediag/knowledge/保存处理这些内容的程序。

知识分为三类：

- 芯片知识：功能、寄存器、状态及使用限制。
- 检测定义：测试前提、操作、失败判据及覆盖范围。
- 诊断依据：候选原因、区分方法及后续检查建议。

关键知识应保留来源、适用芯片和版本信息。可执行规则与知识依据通过标识或引用关联，避免两处独立维护同一判据。当前知识条目的 `kind` 只使用 `chip_knowledge`，检测定义与诊断依据待后续批次。

### 离线构建与运行检索

离线构建负责资料提取、内容整理、分块、来源标注和索引生成；运行检索从已构建的索引中查询证据，不在每次诊断时重新解析PDF。

首版已实现，代码在 `src/airbornediag/knowledge/`：

- `model.py` 读取并校验 `knowledge/curated/` 下的知识文件。除格式外还核对出处：条目的 `source_id` 必须已在 `knowledge/source-registry.json` 中登记，且条目的 `chip` 在该来源的 `applies_to` 范围内——来源未覆盖的芯片不能写成该来源的知识。
- `index.py` 用 SQLite FTS5 构建索引并查询。中文按单字切分、英文按词切分，查询时连续中文合并为一个短语、各词之间取交集，因此中文按子串命中、寄存器名不区分大小写；过滤条件为芯片与外设，排序由 `bm25` 决定。
- 命令行入口为 `airbornediag kb build` 与 `airbornediag kb query`，参数与退出码见 [development.md](development.md)。

知识条目以「一条可独立引用的依据」为粒度，每条对应一个可核对的出处，使用章节号与表/图编号定位。

索引是本地生成物，不提交仓库；构建为整表重建，重复执行不产生重复条目。首版不引入向量检索，后续根据检索效果再决定。检索效果由 `tests/test_knowledge_search.py` 用代表性查询覆盖；**板端构建与查询尚未执行**。

### 模型与输出

确定性解析、位运算和数值比较由代码完成。模型根据输入、工具结果及检索证据进行综合分析和解释。

模型调用是流程中的一环，不是可选的润色步骤：**调用失败即该环节失败，不得降级为模拟回答、缓存内容或省略后的"正常"结论**。模型不可用时，流程应如实报告未能取得分析，而不是给出看似完整的报告。

报告应区分：

- 已观测到的异常；
- 规则确认的状态；
- 待验证的候选原因；
- 引用依据；
- 缺失信息；
- 排查与处理建议。

输出校验检查结构、必要字段和引用有效性（当前由 `scripts/validate_contracts.py` 承担），但校验通过不代表诊断结论必然正确。诊断质量需要使用独立的预期结果评估。

首版仅输出建议，不自动控制设备。

## 开发与部署关系

现有Qwen2.5-1.5B-Instruct已在RDC300I上通过MindIE部署。

在Windows开发应用，通过HTTP访问现有模型服务，再将应用部署至RDC300I。请求格式按板端可运行的历史脚本确认并实现，接口、配置项与退出码见 [development.md](development.md)。**真实调用已在板端验证通过**（板端本机执行）；Windows直连板端服务的连通性仍是遗留项。

模型权重独立于代码仓库，由推理环境加载。应用通过模型客户端访问服务，不直接依赖某个模型文件夹路径。

应用依赖与MindIE推理环境分开管理。原始资料、生成的索引和运行输出按各自用途管理，不随代码一并无差别提交。

## 后续扩展原则

- 新增MCU时补充对应专用逻辑、知识与测试案例，复用统一流程。
- 接入实际控制器时增加输入适配器。
- 更换模型服务时调整模型适配层。
- 升级检索方式时保持上层检索结果结构稳定。
- 仅在实际需求出现时增加目录和抽象，不提前建设通用插件框架。

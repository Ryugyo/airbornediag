# AirborneDiag 架构说明

## 当前状态

当前工程已建立可安装的 Python 包、命令行入口和测试，定义了输入输出契约与首批诊断场景，实现了对 MindIE 模型服务的调用，建立了首批 MCU 诊断知识库与全文检索，实现了 MPC5554 的 FlexCAN2 与 DSPI 首批诊断工具，并打通了从故障记录到诊断报告的完整流程。

本文记录已确定的模块划分和首版处理流程。环境配置、安装、知识库构建与查询、模型服务接口、诊断工具与完整流程的用法、测试方法见 [development.md](development.md)，字段语义与约束见 [contracts.md](contracts.md)，场景与判据依据见 [scenarios.md](scenarios.md)。

## 首版处理流程

统一故障JSON输入 → 数据校验 → MCU相关工具分析与知识检索 → Qwen综合分析 → 输出校验 → 结构化诊断报告。

首版由程序固定编排处理步骤，不依赖模型自主选择工具。

输入采用模拟故障记录。未来通过控制器专用适配器转换实际记录，复用统一诊断流程。

应用包内已建立：

- `__init__.py`：包定义与版本号。
- `cli.py`：命令行入口，支持使用说明、版本查询与 `llm`、`kb`、`diag`、`report` 子命令。
- `config.py`：配置加载与校验，当前只包含模型服务配置。
- `llm/`：模型服务调用与诊断环节。`client.py` 负责请求与响应处理，`prompt.py` 负责通用提示词构造，`diagnosis.py` 负责诊断提示词与模型回答的解析。
- `knowledge/`：知识读取、索引构建与查询，不依赖模型服务。`model.py` 负责知识文件读取与出处校验，`index.py` 负责索引与检索。
- `mcu/`：诊断工具，不依赖模型服务，也不依赖知识检索。`model.py` 是工具结果模型，`record.py` 是故障记录的只读视图，`tools.py` 负责分派与范围报告，`mpc5554/` 下每个外设一个模块。
- `pipeline.py`：完整流程编排，把上述环节按固定顺序串起来。
- `report.py`：诊断报告的组装与跨文档校验，运行期自检与仓库校验脚本共用同一份实现。

后续计划在应用包内按需建立：

- schemas.py：输入、输出及内部数据模型。

该文件尚未实现。独立职责初期可以由单个文件承担，内容增长后再拆分为包。

## 核心边界

### 统一输入与控制器适配

统一JSON描述目标MCU、检测上下文和观测信息，字段约束由 [schemas/](../schemas/) 下的 JSON Schema 声明，语义与缺失值约定见 [contracts.md](contracts.md)。

控制器原始PBIT记录的解释依赖控制器型号、软件版本和检测定义。未来输入适配器负责这类转换，不将控制器专有故障码混入通用MCU逻辑。

缺失信息表示未知，不能自动转换为正常状态或默认测量值。

### MCU工具与诊断编排

MCU模块负责有依据的寄存器解码、状态解释和专用判据计算。

工具结果应能够表达：

- 解析得到的事实；
- 适用的规则及来源；
- 数据不足或不适用的原因；
- 有依据支持的候选结论。

流程编排负责组合相关工具和检索结果。后续跨外设关联分析由流程组织，避免各MCU模块自行复制整套诊断流程。

未实现或未验证的故障类型应明确报告支持范围，不能默认为正常。

首批工具已实现，代码在 `src/airbornediag/mcu/`，命令行入口为 `airbornediag diag`：

- 工具结果把确认状态、输入矛盾、缺失信息与不支持项分开表示。每条状态与矛盾带观测证据、文献出处，以及它在知识库中对应的条目 id；缺失信息也带判定依据——「缺少它就下不了结论」本身往往是手册里的一条规则（例如读清除位的覆盖区间），只有记录里没有任何观测、不存在被应用的判据时才不挂依据。
- 记录被读成只读视图：按模块实例取寄存器观测，按位域跨观测汇总取值。同一字段出现多个不同取值时不合并，由规则报缺失而不是挑一个当作当前值；本版不比较观测时刻、不做跨观测的时序分析，因此只说明「存在多个不同取值」，不声称它们来自不同采集时刻。
- 分派按芯片与检测对象确定，并集中报告不属于本版范围的内容：不支持的芯片、手册实例清单之外的模块名、没有判据的检测对象、只给原始值的观测、不合契约的寄存器名、没有判据的观测种类，以及**已观测但本版没有判据的位域与寄存器**（后者附观测 id，不能被读成未观测）。
- `mpc5554/` 下每个外设一个模块，模块内是普通函数，不建设通用规则引擎。
- 工具本身不产生候选根因：根因需要结合知识检索与模型分析，由编排环节中的模型负责，工具只给出有依据的状态与缺失信息。

首版只使用记录中已解码的位域。按位解释寄存器原始值需要逐条核对位编号，位编号尚未入知识库，因此只给出 `value` 的观测一律报告为不支持，不猜其含义。反过来，位域已解码而本版还没有判据时按「已观测但没有判据」列出并附观测 id，**不能被读成未观测**：两者都不参与判断，但与「记录中没有该观测」是两回事。

### 知识资料与知识处理代码

根目录knowledge/保存资料及整理后的知识；src/airbornediag/knowledge/保存处理这些内容的程序。

知识分为三类：

- 芯片知识：功能、寄存器、状态及使用限制。
- 检测定义：测试前提、操作、失败判据及覆盖范围。
- 诊断依据：候选原因、区分方法及后续检查建议。

关键知识应保留来源、适用芯片和版本信息。可执行规则与知识依据通过标识或引用关联，避免两处独立维护同一判据：诊断工具中的每条结论在 `basis.knowledge_refs` 里列出它依据的知识条目 id，`tests/test_mcu_tools.py` 校验这些 id 在 `knowledge/curated/` 中确实存在。当前知识条目的 `kind` 只使用 `chip_knowledge`，检测定义与诊断依据待后续批次。

### 离线构建与运行检索

离线构建负责资料提取、内容整理、分块、来源标注和索引生成；运行检索从已构建的索引中查询证据，不在每次诊断时重新解析PDF。

首版已实现，代码在 `src/airbornediag/knowledge/`：

- `model.py` 读取并校验 `knowledge/curated/` 下的知识文件。除格式外还核对出处：条目的 `source_id` 必须已在 `knowledge/source-registry.json` 中登记，且条目的 `chip` 在该来源的 `applies_to` 范围内——来源未覆盖的芯片不能写成该来源的知识。
- `index.py` 用 SQLite FTS5 构建索引并查询。中文按单字切分、英文按词切分，查询时连续中文合并为一个短语、各词之间取交集，因此中文按子串命中、寄存器名不区分大小写；过滤条件为芯片与外设，排序由 `bm25` 决定。
- 命令行入口为 `airbornediag kb build` 与 `airbornediag kb query`，参数与退出码见 [development.md](development.md)。

知识条目以「一条可独立引用的依据」为粒度，每条对应一个可核对的出处，使用章节号与表/图编号定位。

索引是本地生成物，不提交仓库；构建为整表重建，重复执行不产生重复条目。首版不引入向量检索，后续根据检索效果再决定。检索效果由 `tests/test_knowledge_search.py` 用代表性查询覆盖，Windows 与板端均已执行通过。

### 流程编排与报告组装

完整流程由 `airbornediag report` 提供，代码在 `src/airbornediag/pipeline.py`，固定顺序为：输入校验 → 工具分析 → 知识检索 → 模型分析 → 报告组装与自检 → 输出。各环节的实现与单独执行时完全相同，编排层只负责串接与传递，不复制判据，也不让模型选择工具。

职责边界按「谁有依据谁写」划分：

- **程序保留的字段**：`device`、`test`、`observations` 按输入记录原样保留，`confirmed_states`、`inconsistencies`、`insufficient_data`、`unsupported`、`fault_state` 与 `root_cause` 由工具结论直接组装。模型不得改写这些内容，运行期自检会逐字段比对。
- **模型负责的部分**：解释、候选原因与检查建议。候选原因的证据引用只能是记录中已有的观测，引用不存在的观测即判为不合规并终止流程。
- **对象归属**：规则 id 不含模块实例名，同一外设的多个实例会产生同名规则，因此报告中的状态 id 统一写为 `<检测对象>/<规则 id>`，保证唯一可辨且规则来源可读。
- **检索顺序**：优先取工具结论 `basis.knowledge_refs` 指向的知识条目并全部保留，再用工具使用到的位域名按芯片与外设补充，去重后按上限截断。

### 模型与输出

确定性解析、位运算和数值比较由代码完成。模型根据输入、工具结果及检索证据进行综合分析和解释。

模型调用是流程中的一环，不是可选的润色步骤：**调用失败即该环节失败，不得降级为模拟回答、缓存内容或省略后的"正常"结论**。模型不可用时，流程应如实报告未能取得分析，而不是给出看似完整的报告。

报告应区分：

- 已观测到的异常；
- 规则确认的状态；
- 待验证的候选原因；
- 引用依据；
- 缺失信息；
- 排查与处理建议。

模型回答必须是约定结构的 JSON，引用的观测必须存在，候选原因至少引用一条观测，不合规一律报错并终止，不修补、不重试、不降级。送出的提示词按字符数设有上限，超限时只整条移除**未被工具结论引用**的补充知识条目，并在提示词内写明省略了多少条；观测、工具结论、输入矛盾、缺失信息与工具引用的知识都不截断也不省略，裁到无可再裁仍然超限就直接报错——截断会让模型引用记录中并不存在的证据。

输出校验检查结构、必要字段和引用有效性：Schema 由 `jsonschema` 执行，跨文档关系由 `src/airbornediag/report.py` 承担，运行期自检与 `scripts/validate_contracts.py` 共用同一份实现。校验通过不代表诊断结论必然正确，诊断质量需要使用独立的预期结果评估。

**模型服务对输入长度的限制已核对**（2026-09-24）：服务端当前输入上限 10240 tokens、生成 2560、总长 12800，且 `truncation=false`；应用侧仍只按字符数控制提示词规模（`PROMPT_CHAR_LIMIT`），取值按实测的 token 密度折算，见 [development.md](development.md)。`truncation` 必须保持 `false`：为 `true` 时服务端会静默截断提示词，模型可能引用被截掉的观测。

**模型自由文本的质量目前不达预期**：真实联调确认程序组装的部分与工具结论逐条一致，但模型未提出候选原因、并在检查建议中写出过材料里不存在的位域名。2026-09-28 针对提示词与解析做过一轮修正（去掉会被照抄的示例、要求 `supporting` 非空、取消会改变证据的硬截断），小样本复测中未再出现回答结构不合规，但候选原因仍为空——**当前知识库缺少成因类条目，按"知识与观测共同支持才提出"的口径给不出候选原因**。这类错误是结构校验拦不住的，见 [development.md](development.md) 的"模型内容质量"。

首版仅输出建议，不自动控制设备。

## 开发与部署关系

现有Qwen2.5-1.5B-Instruct已在RDC300I上通过MindIE部署。

在Windows开发应用，通过HTTP访问现有模型服务，再将应用部署至RDC300I。请求格式按板端可运行的历史脚本确认并实现，接口、配置项与退出码见 [development.md](development.md)。**真实调用已在板端验证通过**（板端本机执行）；Windows直连板端服务的连通性仍是遗留项。

模型权重独立于代码仓库，由推理环境加载。应用通过模型客户端访问服务，不直接依赖某个模型文件夹路径。

应用依赖与MindIE推理环境分开管理。原始资料、生成的索引和运行输出按各自用途管理，不随代码一并无差别提交。

## 后续扩展原则

- 新增MCU时补充对应专用逻辑、知识与测试案例，复用统一流程。
- 接入实际控制器时增加输入适配器。
- 更换模型服务时调整模型适配层。
- 升级检索方式时保持上层检索结果结构稳定。
- 仅在实际需求出现时增加目录和抽象，不提前建设通用插件框架。
